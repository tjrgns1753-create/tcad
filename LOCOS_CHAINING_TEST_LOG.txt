=======================================================

Purpose: track every isolated test/probe run while investigating why a
process step chained onto fresh-LOCOS-built geometry corrupts its own
mesh export (see CLAUDE.md, "LOCOS process-flow chaining"). This is a
TEST-ONLY log per explicit user instruction -- no production code
(tcad/*, tests/*) is modified while these entries are added. Entries
are appended in chronological order, oldest first, and never deleted,
so this stays an honest record of everything tried, including dead
ends.

Each entry: date/session marker, hypothesis, what was run, result,
conclusion.

9. Hypothesis (revised after a probe-construction mistake -- see
   below): is "last-inserted level set survives, everything earlier
   collapses" a general insertion-ORDER rule (independent of material
   identity), or does Mask specifically survive because it is the
   maskMaterial passed to the etch model regardless of position?
   First attempt: built [Mask(0, floating box), Si(1, box), SiO2(2,
   wrap, last)] entirely via explicit insertNextLevelSetAsMaterial
   calls, including calling geometry.getBoundaryConditions() on a
   BRAND NEW domain with zero level sets yet inserted. This segfaulted
   immediately (before any print output at all) -- turned out to be a
   probe-construction bug, not a new finding: this project's own
   tcad/process/oxidation/thermal.py already documents that
   getBoundaryConditions() segfaults on an empty domain, which is
   exactly what the first version of this probe did. Not a new issue,
   just re-discovering an already-known, already-documented
   precondition the hard way.
   Fixed test (Variant B): kept Si as the required first-via-MakePlane
   call (to safely establish the domain, matching the documented-safe
   pattern), then inserted Mask-box SECOND (was third in test 8) and
   SiO2-wrap THIRD/last (was second/middle in test 8) -- i.e. simply
   swapped the insertion order of Mask and the SiO2 wrap relative to
   test 8, keeping everything else identical (same box, same wrap,
   same chained directional-etch model).
   Result: with SiO2 (the wrap) now LAST, NEITHER Si (index 0) NOR
   Mask (index 1) collapsed to zero after the chained Process() call
   -- both just shrank in point count in the same unremarkable way
   test 6's non-corrupted baseline did (63->42 for Si, 48->22 for
   Mask). SiO2 itself (now last) was completely unchanged (64 points,
   both before and after).
   Conclusion: this refines (and corrects) the "last inserted
   survives" theory into something more precise and mechanistic: the
   corruption specifically triggers when ANY level set is inserted
   AFTER a wrapped (addToExisting=True / wrapLowerLevelSet=True) level
   set. When the wrap is itself the LAST insertion (tests 6 and 9),
   nothing breaks. When something is inserted AFTER the wrap (test 8,
   and the real LOCOS construction in _build_locos_geometry(), which
   always does Si -> SiO2-wrap -> Mask, in exactly that order), the
   wrap and everything inserted before it collapse to 0 points on the
   next Process() call, while only whatever was inserted after the
   wrap survives. This is now a precise, mechanistically-isolated
   characterization -- not just "LOCOS is buggy," but a specific,
   reproducible ViennaPS behavior: material stacks whose LAST
   insertion is not the wrap-holding level set corrupt under a
   further Process() call. Since LOCOS's real construction always
   inserts the mask AFTER the oxide wrap, it is unconditionally
   exposed to this every time.

SUMMARY (this session's incremental additions, tests 5-10):

The bug is now characterized far more precisely than before this
session's tests. It is NOT specific to LOCOS's mask geometry, contact-
epsilon trick, or prior Oxidation()/mechanics solve (tests 6, 7, 8 all
rule these out individually). It IS specifically triggered by:
inserting any level set AFTER a wrapped (wrapLowerLevelSet=True) level
set, then running ANY further Process() call on the domain (tests 8
vs. 9 vs. 10, three independent constructions, consistent result each
time). LOCOS's actual production construction
(tcad/process/oxidation/thermal.py's _build_locos_geometry) always
inserts the mask box AFTER the SiO2 wrap, so it is unconditionally
exposed every time a further step is chained onto it.

A reordering-based fix candidate (insert the mask BEFORE the wrap, so
the wrap becomes the last insertion) avoids the collapse in two
independent tests, but whether it preserves the ACTUAL LOCOS oxidation
physics (real growth + mask retention, the original bar the shipped
mask-erosion fix had to clear) is unverified and would need a
materially larger follow-up test using the real Oxidation() model, not
attempted this session.

No production code (tcad/*, tests/*) was modified for any test in this
log. All probe scripts (.probe_locos_test*.py) were deleted after each
test, per this project's established scratch-file convention.

12. Attempted to fetch ViennaPS's real advection/Process source from
    GitHub (blocked by a rate limit in the previous test round) --
    THIS TIME IT WORKED. Fetched psDomain.hpp (confirms
    insertNextLevelSetAsMaterial's exact wrap semantics: unions the
    NEW level set with levelSets_.back() -- i.e. whatever was already
    last at THAT moment, not "everything in the domain" -- and that
    getSurface() is defined as simply levelSets_.back(), no separate
    internal pointer) and, decisively, ViennaLS's lsAdvect.hpp, which
    contains the EXACT, documented root cause:

      "Level sets are passed to the constructor in a std::vector, with
      the last element being the level set to advect, or 'top level
      set', while the others are then adjusted afterward... the 'top
      level set' has to include all lower level sets:
      LS_top = LS_top U LS_i for i = {0...n}"

    The "adjusted afterward" step (adjustLowerLayers(), quoted
    verbatim by the fetch) is:
      for i in 0..size-2: BooleanOperation(levelSets[i],
                                            levelSets.back(),
                                            INTERSECT).apply()
    i.e. EVERY level set except the last is intersected against the
    last one. If the last one does not geometrically CONTAIN a given
    lower level set, that intersection produces an EMPTY level set --
    exactly, precisely, the 0-point collapse observed in every test in
    this log.

    This fully and mechanistically explains every result from tests
    6-10, not just describes the symptom:
      - Test 6 (Si, SiO2-wrap-last, 2 level sets): back()=SiO2, which
        by construction (UNION with Si at insertion) already contains
        Si. Precondition satisfied -- no collapse. Matches.
      - Tests 7/8 (Si, SiO2-wrap, Mask-last -- the REAL LOCOS
        construction): back()=Mask, a small bounded box that does NOT
        geometrically contain Si or SiO2's regions at all.
        Precondition violated for BOTH of them -- both go empty.
        Matches exactly (both collapsed to 0 in every real/synthetic
        test of this exact ordering).
      - Tests 9/10 (Si, Mask, SiO2-wrap-last): back()=SiO2. SiO2's OWN
        plane (semi-infinite half-space below its own y, independent
        of what it unioned with) already geometrically contains Si's
        region (also a semi-infinite half-space, at a lower y) as a
        pure coincidence of both being unbounded planes stacked at
        different heights -- and SiO2 explicitly unioned with Mask at
        insertion time too. Precondition satisfied for both -- no
        collapse. Matches exactly.

    This also explains WHY test 11 (real Oxidation() first, THEN
    chained etch, on the test-10 reordered geometry) broke differently
    than test 10's own direct-chain version: since SiO2 in that
    reordering only ever explicitly unioned with Mask (not Si) at
    insertion time -- its containment of Si was purely the semi-
    infinite-plane coincidence noted above, not a real "SiO2 grew on
    top of Si and consumed it" relationship -- the real Oxidation()
    model's own internal mechanics (evaluating oxide growth as
    consuming Si at the true Si/oxide interface) had no valid
    interface to work with, which is consistent with test 11's other
    finding (zero displacement, no real growth) and would plausibly
    leave the domain in a different (still poorly-understood in
    detail) internal state that changes which level set satisfies
    containment on the NEXT Process() call.

SESSION SUMMARY (tests 11-14, this continuation):

Fetched real ViennaLS source (lsAdvect.hpp) once the GitHub rate limit
cleared and found the EXACT, documented root cause: Advect() requires
the last-inserted level set to geometrically contain every other level
set in the domain (adjustLowerLayers() intersects each other level set
against it; violating containment produces an empty result). This
